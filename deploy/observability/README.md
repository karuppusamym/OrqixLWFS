# Orqix observability pack (CG-P06)

Build note: `docs/build/S150-observability-scale-backups-admission.md`.

| Path | What |
|---|---|
| `grafana/dashboards/*.json` | Three dashboards: **Overview and SLOs**, **Connections, polls and AI**, **Operations** (bulk, alerts, analytics, retention). Generated by `grafana/generate_dashboards.py`; edit the script, not the JSON |
| `grafana/provisioning/` | Data sources (Prometheus, Jaeger) and the dashboard provider for the Compose overlay |
| `prometheus/orqix-alerts.yaml` | SLO recording rules and alerts (Prometheus rule file) |
| `prometheus/prometheus.yml` | Scrape configuration for the Compose overlay (finds pods by service name) |
| `../openshift/optional/prometheusrule.yaml` | The same rules as a `PrometheusRule` for OpenShift user-workload monitoring (generated) |
| `../compose/docker-compose.observability.yml` | Prometheus, Grafana and Jaeger next to the Compose stack, traces exported to Jaeger |

`python tools/validate-manifests/validate_manifests.py` checks that the rules are well formed, that the PrometheusRule
equals the rule file, that the dashboards parse, and that every `orqix_*` metric they use is registered in the backend.
Regenerate the PrometheusRule with `--write-prometheusrule`.

## Traces (OpenTelemetry)

Orqix makes OpenTelemetry spans through Micrometer Tracing on every pod: one server span per HTTP request, one span per
engine job (`orqix.job`, a child of the request that started the run), one client span per connector call
(`orqix.connector.call`) and model provider call (`orqix.ai.call`). Poll checks, external worker jobs and AI tasks run
inside engine jobs or scheduler runs and appear under them. The trace id is written to every log line of traced work (MDC
`traceId` and `spanId` in the ECS JSON), to each timeline event (`run_event.trace_id`) and to each effect attempt (`effect_journal.trace_id`), so
an operator can go from a request's history to its trace.

| Setting (env) | Default | Meaning |
|---|---|---|
| `ORQIX_TRACING_ENABLED` | `true` | spans and trace ids; `false` turns tracing off completely |
| `ORQIX_TRACING_SAMPLING` | `1.0` | share of traces recorded and exported; lower it at high volume (0.1) |
| `ORQIX_TRACING_OTLP_ENABLED` | `false` | export spans with OTLP/HTTP |
| `ORQIX_TRACING_OTLP_ENDPOINT` | `http://localhost:4318/v1/traces` | OpenTelemetry Collector, Jaeger, Tempo ... |
| `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_HEADERS_<NAME>` | - | extra header, for example `..._AUTHORIZATION="Bearer <token>"` (from a Secret) |
| `ORQIX_ENVIRONMENT` | `local` | resource attribute `deployment.environment.name` |

Trace context is accepted from callers (W3C `traceparent`, B3) and is **not** sent to connected systems: connector and
model calls do not carry Orqix trace headers (decision S150). Span attributes hold ids, keys, outcomes and status codes,
never request data, prompts or answers.

## Metrics

Prometheus scrapes `/actuator/prometheus` on the management port (8081) of every pod (`../openshift/optional/servicemonitor.yaml`).
Gauges marked *DB* read the database and are identical on every pod; dashboards and rules take `max()` over pods.

| Feature | Metric | Kind |
|---|---|---|
| HTTP API | `http_server_requests_seconds_*{uri,method,status}` (histogram) | timer |
| Requests | `orqix_runs_started_total`, `orqix_runs_completed_total{outcomeKind}`, `orqix_runs_needs_attention` (DB), `orqix_tasks_decided_total{action}` | counters, gauge |
| Engine jobs | `orqix_oldest_executable_job_age_seconds` (DB) | gauge |
| Connector calls | `orqix_connector_call_seconds_*{effect_class,outcome}` (histogram), `orqix_effect_attempts_total{class,outcome}` | timer, counter |
| Circuits (CG-C09) | `orqix_connection_circuits{state=open\|halfOpen}` (DB) | gauge |
| Poll checks (CG-W01/W03) | `orqix_poll_checks_total{outcome}`, `orqix_poll_waits_active`, `orqix_poll_waits_due`, `orqix_poll_check_lag_seconds` (DB) | counter, gauges |
| Bulk operations (CG-O03) | `orqix_bulk_items_total{action,outcome}`, `orqix_bulk_operations_running` (DB) | counter, gauge |
| Alerts (CG-O05) | `orqix_alerts_fired_total`, `orqix_alerts_resolved_total`, `orqix_alert_notifications_total`, `orqix_alert_incidents_open` (DB) | counters, gauge |
| Analytics (CG-N) | `orqix_analytics_lag_seconds`, `orqix_analytics_outbox_pending`, `orqix_analytics_outbox_dead` (DB) | gauges |
| AI tasks (CG-A) | `orqix_ai_tasks{status}`, `orqix_ai_task_queue_age_seconds` (DB), `orqix_ai_tasks_ended_total{status}`, `orqix_ai_call_seconds_*{server_address,outcome}` | gauges, counter, timer |
| Admission (CG-P05) | `orqix_admission_rejected_total{kind=start\|message}` | counter |
| Pods | `hikaricp_connections_*`, `jvm_*`, `process_cpu_usage` | Micrometer defaults |

## Service level objectives

Measured over a rolling 30 days. They are the targets the dashboards and alerts are built on; the numbers measured on
one machine are in the build note.

| SLO | SLI (PromQL) | Target | Alerts |
|---|---|---|---|
| API availability | 1 - 5xx / all requests on `/api/**` (`orqix:api_error_ratio:*`) | 99.5 % (error budget 0.5 %, about 3.6 h per 30 days) | `OrqixApiErrorBudgetFastBurn` (14.4x over 1 h and 5 m, page), `...SlowBurn` (6x over 6 h, ticket) |
| Start latency | p95 of `POST /api/v1/workspaces/{workspaceId}/runs` (`orqix:start_latency_p95:5m`) | 95 % within 1 s | `OrqixStartLatencyHigh` (15 m) |
| Read latency | p95 of `GET /api/**` (`orqix:read_latency_p95:5m`) | 95 % within 500 ms | `OrqixReadLatencyHigh` (15 m) |
| Job freshness | `max(orqix_oldest_executable_job_age_seconds)` | below 60 s 99 % of the time | `OrqixEngineJobsStale` (10 m, page) |
| Analytics freshness | `max(orqix_analytics_lag_seconds)` | below 5 min 99 % of the time | `OrqixAnalyticsLagging` (15 m) |

Not SLOs but alerted: pods not scraped, connection pool waits, requests needing attention rising, open circuits, poll
checks running late, dead analytics projections, AI task backlog, admission refusals (info: a workspace is at its limit).

The availability SLI counts 4xx answers as served, including a 429 from admission control (a deliberate limit, not a
failure). Failures of connected systems are not API errors: they surface as effect outcomes and circuit states.

## Compose

```bash
cd deploy/compose
docker compose -f docker-compose.yml -f docker-compose.observability.yml --profile app --profile observability up -d
```

Grafana http://localhost:3000 (folder Orqix), Prometheus http://localhost:9090 (Alerts tab), Jaeger http://localhost:16686
(service `orqix`). Add `-f docker-compose.roles.yml` for the API + two worker pods.

## OpenShift

1. Enable user-workload monitoring for the namespace, then `oc apply -f deploy/openshift/optional/servicemonitor.yaml`
   and `oc apply -f deploy/openshift/optional/prometheusrule.yaml`.
2. Import the three dashboards into the Grafana instance that reads the cluster's Thanos querier; select that data source
   in the dashboard's *Prometheus* variable.
3. For traces, run an OpenTelemetry Collector (Red Hat build of OpenTelemetry) and set `ORQIX_TRACING_OTLP_ENABLED=true`
   and `ORQIX_TRACING_OTLP_ENDPOINT` in the overlay's `config.env`; allow egress from the Orqix pods to the collector's
   port 4318 (add a NetworkPolicy like `orqix-allow-connection-egress`).
