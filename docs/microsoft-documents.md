# SharePoint and OneDrive document references

The first document integration uses Microsoft Graph through an approved, versioned connection. A normal **Call a system** step maps `driveId`, `itemId`, and `versionId` from request fields into the connection operation. The returned document name, selected version, text, and SHA-256 digest can feed later decisions, bounded agents, approval tasks, and final outputs.

This slice reads metadata and historical UTF-8 text versions, extracts bounded PDF and OOXML Office text, and captures current content as an immutable retained snapshot. It does not browse a tenant, upload files, refresh OAuth tokens, or impersonate the requester. Microsoft permissions apply to the server credential in the workspace binding; Orqix permissions control who can administer that binding and start or inspect the workflow. A service credential's access does not prove that an individual requester has access in Microsoft.

## Configure an approved connection

1. Register [the example connection definition](../examples/connections/microsoft-documents-v1.json) through the existing connection-version endpoint as a workspace administrator. For a tenant-specific contract, restrict `driveId` with a `requestSchema.properties.driveId.enum` on every operation. Access scopes and selected-resource grants must also restrict the service identity in Microsoft.
2. Approve `graph.microsoft.com:443` and the exact download authority used by the tenant in the deployment egress allowlist. Download URLs use expiring query credentials; the policy approves their authority, rejects URL user information and fragments, checks DNS/address restrictions, and retains no signed URL. Plain HTTP is available only to explicitly configured development hosts for stub tests.
3. Mount a bearer-token secret using the existing `orqix.secrets.dir` mechanism. Set the binding to `https://graph.microsoft.com/v1.0`, `auth.type=bearerToken`, its `secretRef`, and `enabled=true`. The token is read on every call so an external credential service can rotate it. Automatic client-credential acquisition and refresh remain a separate delivery item.
4. In workspace connection settings, provide drive, item, and version IDs to test an operation. The test checks access and returns an outcome and safe provenance fields, including a snapshot ID after capture. It does not return extracted document text to the browser.
5. Import [the document-review workflow](../examples/document-review.json), publish it after selecting the workspace manager group, and start it with the three identifiers. It reads the selected version, waits for a manager, and records the document name, version and content digest in its result.

Microsoft Graph documents separate item content downloads from version content downloads. The version endpoint does not support downloading the current version; this slice deliberately uses historical version content and returns a visible failure rather than substituting the latest file. [Item-content API](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0), [version-content API](https://learn.microsoft.com/en-us/graph/api/driveitemversion-get-contents?view=graph-rest-1.0).

For scoped app access, Microsoft Graph provides selected permissions with resource grants. Actual tenant setup, admin consent, and resource grants are required outside the local test environment. [Selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview).

## Runtime contract

The connection kind is `microsoftGraph`; its operations are portable `POST /metadata`, `POST /text`, `POST /extract`, `POST /pinLatest`, and `POST /extractSnapshot` adapter contracts, with `effectClass=readOnly` and success status 200. Those operation paths are not sent as POST requests to Graph. The adapter translates mapped input into authenticated Graph GETs and uses the existing effect journal, response-schema validation, result mapping, retries, and operator recovery.

`/metadata` reads the item and, when supplied, its version metadata. `name`, `webUrl`, and `eTag` describe the current item; `size` and `lastModifiedDateTime` describe the selected version. `/text` requires a nonempty `versionId`; it returns those fields plus `text` and `contentSha256`. Missing or inaccessible versions fail without a latest-version fallback. Repeated attempts retain the pinned reference. The content hash provides evidence of the exact bytes read.

Only one 302 redirect is followed for document content. The redirected request never contains the Graph Authorization header. Both Graph and download requests disable automatic redirects. Signed download URLs, credentials, and remote response diagnostics are excluded from results and error details. Permission failures are permanent; rate limiting, timeouts, and server unavailability use the existing read-only retry classification.

Content must be a text MIME type or JSON, decode as UTF-8 without malformed byte sequences, contain no NUL character, and fit within 64 KiB. Size is checked against version metadata and enforced again by the streaming response subscriber. A single wall-clock deadline bounds all requests in the operation. The `/text` operation rejects PDF and Office content. Alternative text charsets, folders, invalid identifiers, and unapproved download authorities fail visibly.

Document text becomes workflow data only when explicitly mapped. Treat it as untrusted source material in any agent instruction; it is not permission to execute operations suggested by the document. Normal run visibility and data-retention policies apply to mapped text.

## PDF and Office extraction

Register [connection version 2](../examples/connections/microsoft-documents-v2.json) after version 1 to add `extractDocument`, `pinLatest`, and `extractSnapshot`. The [snapshot-review example](../examples/document-snapshot-review.json) captures current content, extracts the immutable captured bytes, and waits for a manager. Historical extraction continues to require a real `versionId`; current snapshots never masquerade as historical Graph versions.

`/extract` accepts pinned historical PDF, DOCX, XLSX, or PPTX files up to 5 MiB. Apache PDFBox 3.0.6 extracts PDF text; bounded JDK ZIP/StAX readers extract OOXML text without evaluating formulas, running macros, fetching linked content, or resolving external XML entities. XLSX extraction uses stored/cached cell values, not formula recalculation. DOCX body text and PPTX slide text are extracted; comments, notes, embedded objects, charts, formatting, and document layout are not reconstructed. Scanned PDFs without a text layer return `DOCUMENT_TEXT_UNAVAILABLE`; encrypted PDFs and legacy binary or macro-enabled Office documents are rejected.

Parsers run in a separate JVM with a 128 MiB Java heap and 64 MiB metaspace cap. Two parser workers can run concurrently; excess work returns a retryable busy outcome. The parent kills an unfinished worker at the operation deadline. The worker reads only its locally staged file and writes bounded extracted text; document scripts, macros, links, and formulas are never executed. This is process isolation with Java heap/metaspace bounds, not a total operating-system memory cap or a replacement for malware scanning. PDF limits include 100 pages; OOXML limits include 256 entries, 20 MiB total expanded data, expansion-ratio checks, XML depth/event limits, 100 slides/sheets, and 10,000 cells per sheet. Output is limited to 64 KiB of UTF-8 text. Invalid or over-limit documents fail rather than silently returning truncated text.

The executable Spring Boot jar starts the worker through `PropertiesLauncher`; a normal test/class directory uses the same worker main on its classpath. Packaging verification must exercise both PDF and Office parsing through the executable jar and the standard runtime image. [PDFBox documentation](https://pdfbox.apache.org/3.0/migration.html), [JDK StAX input-factory controls](https://docs.oracle.com/en/java/javase/21/docs/api/java.xml/javax/xml/stream/XMLInputFactory.html).

## Capturing latest as a durable snapshot

`/pinLatest` takes `driveId` and `itemId`, reads current item metadata, downloads current content, then reads metadata again. A missing or changed eTag, item mismatch, size mismatch, or changed source during capture fails with `DOCUMENT_CHANGED_DURING_CAPTURE`. It retains the downloaded bytes with their SHA-256 hash and returns `snapshotId`, `eTag`, `contentSha256`, `pinMode=snapshot`, and `snapshotExpiresAt`. Credentials and signed download URLs are never stored. Concurrent admissions are serialized per workspace; identical document/eTag/hash captures deduplicate to the same immutable snapshot and can extend its expiry.

`/extractSnapshot` takes the drive/item reference and `snapshotId`. It loads the exact retained bytes scoped to the current workspace and approved connection key, then extracts them. It makes no request for the latest source file. Source edits or deletion therefore cannot replace previously captured content. Current binding enablement, credential availability, and workflow permissions still apply; retained snapshots are workspace integration data, not Microsoft delegated-user access.

Storage is bounded to 100 snapshots and 100 MiB per workspace. Retention uses the configured idempotency retention period (default 30 days), and safe provenance includes the expiry. Expired snapshots referenced by active runs are retained: references in run input or effect results protect them during running, waiting, or needs-attention states. Completed-run history keeps provenance but does not promise permanent file retrieval. Expired unpinned bytes are removed on subsequent capture; a later extraction of an expired unpinned snapshot fails visibly rather than re-downloading latest. Administrators must choose retention suitable for their business records before enterprise deployment.

`DocumentExtractionTest` exercises PDF/DOCX/PPTX/XLSX parsing in real worker JVMs, encryption and scanned-file rejection, XML entities, macros, output/depth/entry/page/expansion bounds, and supplies fixtures for executable-jar/image checks. `DocumentSnapshotWorkflowTest` covers capture deduplication, source-change races, exact snapshot retrieval after source changes, workspace/connection isolation, quota/expiry behavior, active-run protection, and a published capture/extract/approval workflow.

Current packaging verification: PDF and DOCX fixtures parse successfully through `PropertiesLauncher` in both the executable jar and the standard read-only/non-root Docker runtime with writable `/tmp`. The 7 parser tests, 14 adapter tests, 4 snapshot integration tests and historical-document workflow test pass.
