# MASTER BUILD PROMPT
# Universal AI-Native Workflow Platform
## Production-First | OpenShift | Flowable OSS | React | PostgreSQL

### 1. Your Role

Act as a team of senior enterprise architects, BPMN specialists, AI platform engineers, full-stack developers, UI/UX designers, security architects, DevOps engineers, and QA automation engineers.

Design and implement a production-oriented, lightweight, enterprise-grade, AI-native workflow orchestration platform.

**This is NOT a proof of concept or throwaway demonstration.**

The application demonstrated in 72 hours must be the same application that will subsequently be deployed into production. Implement the most important features first, but do not create temporary architecture, simulated execution engines, or disposable components.

Prioritize working software, production-quality architecture, excellent usability, open standards, extensibility, and operational simplicity.

### 2. Product Vision

Build a universal workflow platform combining:

- PEGA-style business process and case workflows
- Camunda-style BPMN execution
- n8n-style visual workflow creation
- AI-native agent orchestration
- MCP tool discovery and execution
- Human-in-the-loop approval processes
- Rules and decision management
- Enterprise identity and governance
- Conversational workflow generation
- Portable, Git-versioned workflow definitions
- Workflow migration from PEGA, Camunda, and LWFS
- Event-driven and scheduled execution

The platform must support business users, analysts, engineers, administrators, and AI agents.

### 3. Mandatory Architecture Decisions

Use the following technology stack.

**Frontend**
- React + TypeScript + Vite
- React Flow / XYFlow for the primary visual canvas
- BPMN.js for BPMN editing and visualization
- Tailwind CSS
- shadcn/ui
- Zustand
- TanStack Query
- Monaco Editor
- ELK.js for auto-layout

**Backend**
- Java 21 LTS
- Spring Boot, using a compatible supported version
- Flowable OSS BPMN/DMN/CMMN components where applicable
- Spring Security
- Spring Data / JPA where appropriate
- REST APIs
- Server-Sent Events or WebSocket for execution updates

**Database**
- PostgreSQL for production and integration environments
- Database migrations through Flyway or Liquibase
- JSONB for flexible metadata where appropriate
- No mandatory pgvector dependency
- SQLite may be used only for separate lightweight tooling or local metadata components, not as the Flowable clustered execution database

**Infrastructure**
- OpenShift Container Platform
- Multiple application pods
- PostgreSQL HA service
- Kubernetes Secrets / approved enterprise secret management
- Optional Kafka
- No mandatory Redis
- No mandatory Python backend
- No mandatory Temporal
- Container-based deployment

**Language neutrality**

The platform's core backend must be Java-based.

Python, Node.js, .NET, Go, and other technologies must be supported through HTTP APIs, OpenAPI, MCP, A2A-compatible adapters, event messaging, and external workers.

Do not embed a Python runtime merely to execute Python-based agents.

### 4. Architecture Principles

1. One core workflow execution engine: Flowable OSS.
2. One mandatory backend language: Java.
3. One primary frontend framework: React.
4. PostgreSQL is the source of truth for durable workflow state.
5. No mandatory Kafka or Redis dependency.
6. No custom replacement for Flowable's BPMN execution semantics.
7. Modular monolith initially, with separately scalable workers or adapters where necessary.
8. All external integrations must be replaceable.
9. Use standard APIs and portable workflow definitions.
10. Enforce security at every layer.
11. Support multiple OCP pods safely.
12. Use immutable workflow versions for running instances.
13. Keep AI reasoning separate from deterministic process control.
14. Never expose credentials in exported workflows.
15. Keep the application usable without configuring an LLM.

### 6. Workflow Definition and Portability

Create a documented, versioned, portable workflow specification.

Support JSON and YAML representations.

Provide BPMN 2.0 import/export for the supported executable subset.

Definitions must include:
- Schema version
- Workflow identity
- Metadata
- Input/output schemas
- Nodes and transitions
- Triggers
- Rules
- Retry policies
- Timeouts
- Error handling
- Human tasks
- Agent references
- Tool references
- MCP references
- Child workflows
- Execution settings
- Security requirements
- Dependency versions

Separate portable workflow definitions from deployment-specific configuration.

Create a compiler/translation layer that converts the canonical definition into valid Flowable BPMN and DMN artifacts.

Preserve source mappings and identify unsupported constructs.

Avoid claiming universal lossless BPMN round-trip compatibility.

**AI workflow generation**

"Create an employee onboarding workflow with manager approval, IT access provisioning, HR notification, and Teams confirmation."

The system should:

2. Generate a draft workflow.

### 25. Implementation Instructions

Begin by inspecting the repository and existing code.

If no repository exists, initialize the project.

Then:
1. Produce a concise architecture and repository structure.
2. Identify Flowable OSS capabilities and licensing constraints.
3. Define the workflow data model and execution interfaces.
4. Implement the smallest complete end-to-end workflow.
5. Build the real visual editor around that implementation.
6. Add AI-native and connector capabilities incrementally.
7. Add migration functionality.
8. Package for OpenShift.
9. Run automated tests.
10. Document what is complete and what remains.

Do not stop after producing architecture diagrams or documentation.

Proceed with implementation, run the application, validate functionality, and provide a working demo.

**Critical requirement:** The demonstrated codebase must be the foundation of the production application. No architectural rewrite should be planned after the demo. Production deployment still requires all applicable security, resilience, integration and operational gates to pass.
